# Stable web release evidence template

Copy this file for each release candidate. Keep plaintext evidence in the
approved private store and never commit customer names, phone numbers, VINs,
message text, photo content, tokens or production credentials. The public
repository workflow accepts only AES-256-GCM encrypted evidence.

## Go/no-go decision

For each required V2 gate attach command/exit code, measured value, pre-agreed
threshold, environment, release/artifact identity, execution date, evidence URI,
owner, reviewer and dependency references. The release promotion checker requires
all 54 fixed V2 IDs to be explicitly `pass`; required gates cannot be waived.
Local summaries and checkmarks alone are not sign-off.

Technical admission to real data requires all A–D gates in
`PILOT_SCOPE_FREEZE.md`, plus applicable participant consent. Pilot completion
additionally requires all E gates and the signed decision on this candidate.
Any required missing/failed/stale evidence, open P0/P1, unresolved privacy/legal
gap, failed restore or inconsistent booking snapshot is an automatic `NO-GO`.
Required security/data/release gates cannot be waived in this template.

The immutable promotion check is intentionally separate from local diagnostics:

```bash
PUBLISHED_MIGRATION_MANIFEST=/secure/applied-migrations.json \
RELEASE_EVIDENCE_FILE=/secure/release-evidence.json \
RELEASE_ARTIFACT_PATH=/secure/autocare-hub-artifact.tgz \
npm run check:release-promotion
```

The migration manifest must contain the checksummed sources already applied to
the target database. A changed published migration is blocked and requires a
forward correction migration; an absent manifest is also a release blocker.
The checked-in `.github/workflows/release-promotion.yml` downloads encrypted
evidence, the migration manifest and build snapshot from one immutable source
run, verifies GitHub artifact attestations and the exact workflow/repository/SHA,
then decrypts evidence only inside the protected production runner before
running this gate. A local checker invocation is diagnostic only; it cannot
replace cryptographic verification and the protected workflow.

### Public-repository evidence handling

Workflow artifacts and metadata in this public repository must be treated as
public. Configure `RELEASE_EVIDENCE_ENCRYPTION_KEY` as a protected secret on the
GitHub `production` environment. Generate a base64-encoded 32-byte key once and
store the same value in the operator's approved secret manager and that GitHub
environment; never commit or print it in logs.

Encrypt the private evidence locally, then paste only the resulting encrypted
JSON into the `release_evidence_encrypted` input of
`.github/workflows/release-evidence.yml` (run from `main`, targeting a dev SHA).
The migration
manifest is normalized to migration filenames and SHA-256 values before upload.
The evidence is encrypted again after the workflow binds the artifact hash,
release identity and workflow-run provenance. The promotion workflow verifies
the attestation before decrypting the evidence in its runner. Do not include
plaintext evidence in workflow inputs, comments, artifacts or logs.

```bash
read -r -s RELEASE_EVIDENCE_ENCRYPTION_KEY
export RELEASE_EVIDENCE_ENCRYPTION_KEY
node scripts/protect-release-evidence.mjs encrypt \
  /secure/release-evidence.json /private/tmp/release-evidence.enc.json
unset RELEASE_EVIDENCE_ENCRYPTION_KEY
```

The encrypted evidence and migration-manifest JSON must fit the GitHub
`workflow_dispatch` input limit. The release snapshot is a verified build
snapshot, not a deployment: hosting still builds/runs from its configured
source, and attestation does not prove what is currently serving traffic.
