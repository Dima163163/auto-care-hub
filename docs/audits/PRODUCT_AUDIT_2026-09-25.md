## Приоритеты

- **P1:** исправить до публичного пилота: нарушение прав/приватности, некорректное бронирование, существенное искажение условий или поломка основного сценария.
- **P2:** исправить до широкого запуска: функциональная недоработка, надёжность, доступность, SEO либо локальный инфраструктурный риск.
- **P3:** качество текста и подачи, не блокирующее основной сценарий само по себе.
- **Браузер/API:** воспроизведено. **Код:** прямое следствие реализации, без отдельного масштабного или аварийного прогона. **Пробел продукта:** отсутствует необходимый законченный сценарий; это не доказательство внешней атаки.

В исходном срезе отчёта 40 пунктов. После него выполнен отдельный проход исправлений; актуальное распределение закрытых, частичных и заблокированных пунктов приведено в разделе «Статус исправлений» в конце файла. Не все пункты являются уязвимостями безопасности.

## Подробный список

### A01. P1 — Страница заявок сжимает карточки до 123 px

**Статус: исправлено в этом проходе по поручению пользователя. Браузер, измерение DOM, скриншот пользователя.**

При ширине окна 1149 px оболочка кабинета оставляет странице 917 px. Внутри снова создаются три колонки: 220 px, остаток, 280 px. Центральная секция дополнительно делит заявки на две колонки по viewport-брейкпоинту `lg`. Измеренная ширина каждой карточки — 123 px; статусы выступают за границы, названия и цены превращаются в узкие вертикальные столбцы. Горизонтального скролла всего документа при этом нет: обычная проверка `scrollWidth` этот дефект пропускает.

**Где:** `src/pages/profile-bookings/ui/ProfileBookingsPage.tsx`, `AutoCareRequestsPanel.tsx` в той же папке; исходные трёхколоночная сетка и `lg:grid-cols-2`.

**Исправление:** удалена дублирующая внутренняя навигация, заявки занимают ширину страницы, вспомогательные блоки идут ниже. Для карточек максимум две колонки, только когда их собственный контейнер достаточно широк; заголовок и статус могут переноситься.

**Приёмка:** 390/768/1024/1149/1440 px, открытое и свёрнутое меню; никаких трёх колонок основной страницы, наложений, обрезанных статусов и горизонтального переполнения. Карточку и переписку можно открыть.

### A02. P1 — API принимает заявки на прошедшее время

**Подтверждено API и отображением в кабинете.** После 10:00 по Москве отправлена заявка с `preferredAt=2026-09-25T08:00:00+03:00`; API вернул 200 и создал `awaiting_reply`. Это не только ошибка подписи календаря: прошлый визит реально сохраняется в базе.

**Причина:** `request-input-policy.ts:108` проверяет формат даты, но не будущее; `autocare-request.service.ts:1070` передаёт дату в создание и проверку расписания без обязательного запрета прошлого.

**Последствия:** бессмысленные заявки, неверные показатели просрочек, возможность запуска дальнейших действий над визитом, который не мог быть согласован вовремя.

**Исправить:** единая серверная проверка будущего времени и минимального допустимого интервала до визита. Применять её непосредственно перед записью, в том числе для внутренних вызовов. **Приёмка:** вчера, прошедший слот сегодня и дата, успевшая устареть во время заполнения, отклоняются без создания заявки; валидное будущее принимается.

### A03. P1 — Участник может уничтожить контекст разбирательства

**Подтверждено API.** Владелец отправляет два сообщения, клиент жалуется на второе. Удаление первого во время открытого дела возвращает 200, текст становится `null`. Само обжалуемое сообщение пока защищено и возвращает 409. После закрытия дела его тоже удалось удалить в пределах пяти минут.

**Где:** `server/src/modules/autocare/autocare-chat.service.ts:622–650`. Защита проверяет только прямую ссылку `reportedMessageId` у pending-жалобы; неизменяемого снимка контекста нет.

**Последствия:** модератор получает неполную картину; после закрытия невозможно надёжно перепроверить решение или рассмотреть обжалование.

**Исправить:** согласованная политика сохранения доказательств: снимок сообщений и вложений, относящихся к делу, с контролируемым сроком хранения и правами доступа. Не требуется бессрочно запрещать обычное удаление всей переписки. **Приёмка:** удаление пользователем не меняет доказательную версию уже открытого дела; хранение и очистка документированы.

### A04. P1 — Закрытие жалобы не прекращает выдачу её приватного описания

**Подтверждено API.** После закрытия всех дел в чате `GET /v1/chats/:id` для назначенного администратора возвращает 403. Но `GET /admin/chat-reports?status=resolved` продолжает возвращать `description` с маркером `AUDIT_PRIVATE_DESCRIPTION` и текст решения до истечения прежнего TTL.

**Где:** `autocare-chat.service.ts:688–701`: разрешение приватных полей проверяет назначение и срок, но не pending-статус.

**Последствия:** обещание прекращения доступа после закрытия выполняется только для чата. В описании жалобы могут находиться цитаты и другие приватные сведения.

**Исправить:** единая проверка scope/status/expiry для всех поверхностей дела. **Приёмка:** после закрытия, снятия назначения и истечения срока обычный администратор не получает приватные поля ни из чата, ни из списка/деталей дела; разрешённые административные метаданные остаются доступны по явно определённой политике.

### A05. P1 — Администратор без доступа к делу может снимать блокировки

**Подтверждено API.** Владелец создал блокировку клиента. Администратор с закрытым назначением получил 403 при чтении чата, но `DELETE /v1/chats/:chatId/blocks/:blockId` вернул 200 и снял блокировку.

**Где:** `autocare-chat.service.ts`, `revokeAutoCareChatBlock`, примерно строка 671. Для роли Admin разрешено снятие независимо от активного назначения; отсутствует проверка доступа к делу. Для воспроизведения требуется знать идентификаторы чата и блока; это не анонимная атака.

**Последствия:** обычный администратор может вмешиваться в частные ограничения за пределами назначенного scope, например используя ранее известные ID.

**Исправить:** проверять активное назначение, срок и разрешённую операцию; отдельно определить полномочия суперадминистратора и журналировать изменение. **Приёмка:** тот же запрос после закрытия/отзыва/истечения назначения возвращает 403 и ничего не меняет.

### A06. P1 — Отклонённая жалоба позволяет заблокировать человека без причины

**Подтверждено API.** Назначенный администратор отправил решение `{status:'dismissed', blockUser:true}` без `reason`. Ответ 200, причина `null`. Следующая попытка владельца написать сообщение вернула 403.

**Где:** `chat-moderation-policy.ts:101`, `decideAdminAutoCareChatReport` в `autocare-chat.service.ts:808`. `blockUser` не связан с исходом дела, причина необязательна на сервере. Ограничение формы не защищает API.

**Последствия:** жалоба признаётся необоснованной, но наказание всё равно применяется. Нельзя объяснить решение, пересчитать подтверждённые нарушения или объективно рассмотреть обжалование.

**Исправить:** серверная матрица разрешённых исходов и мер; наказание только при обоснованном нарушении либо отдельном документированном основании. Обязательная содержательная причина. **Приёмка:** dismissed+block и любое наказание без причины отклоняются атомарно.

### A07. P1 — Запрет ответной жалобы обходится другим сотрудником сервиса

**Подтверждено API.** Клиент пожаловался на сообщение владельца. После этого написал новое сообщение. Ответная жалоба владельца на него получила 409; такая же жалоба сотрудника того же сервиса получила 200.

**Где:** `chat-moderation-policy.ts:76`, `resolveAutoCareChatReportConflict`: сравниваются user ID, а не сторона конфликта/организация.

**Последствия:** ограничение работает для отдельного логина, но не для сервиса с несколькими операторами. Возможно давление на клиента через коллегу.

**Исправить:** модель сторон дела: клиент и сервис/его представители, с сохранением конкретного автора сообщения. Не запрещать автоматически отдельные более ранние инциденты и обоснованные новые угрозы. **Приёмка:** два сотрудника одной стороны не обходят правила, допустимые исключения связываются с исходным делом.

### A08. P1 — Запчасти и гарантия обещаются без подтверждения данными

**Подтверждено браузером и кодом.** У диагностики показывается «Включая запчасти», хотя API перечисляет только предварительную оценку и фотоотчёт. Любой непустой `warrantyText` превращается в «Гарантия 12 мес.», даже если в нём нет срока. На странице сервиса отдельный блок всегда обещает 12 месяцев.

**Где:** `autocareApiMappers.ts:39`; `ProviderResultCard.tsx:52–55`; `ProviderOfferings.tsx:29`; `ProviderRequestPanel.tsx:97–100`; `ProviderPreviewSection.tsx:193`.

**Последствия:** клиент выбирает услугу на основании условий, которых сервис не предлагал; возникают ценовые споры и претензии к платформе.

**Исправить:** выводить фактический состав и текст/структурированный срок гарантии. Не выводить положительное обещание вместо отсутствующих данных. **Приёмка:** услуга без запчастей и гарантия «30 дней» корректно отображаются во всех карточках, сравнении и подтверждении.

### A09. P1 — При переходе к записи теряется выбранная услуга

**Подтверждено браузером и кодом.** На главной сравнивались тормозные работы за 3500 ₽. Переход «Выбрать и записаться» открыл профиль, где по умолчанию выбрана диагностика за 1200 ₽. Ссылки поиска также могут вести на `/request` без `service`.

**Где:** `mapAutoCareDiscoveryItem` не переносит идентичность услуги в `serviceIds`; `ProviderResultCard.tsx:56` использует `provider.serviceIds?.[0]`; `AutoCareProviderPage.tsx:64–65` выбирает первое предложение; ссылки `ProviderPreviewSection` не сохраняют выбор.

**Последствия:** пользователь может отправить заявку на другую работу и по другой цене. **Исправить:** передавать service/offering/location через все переходы и возвращение к поиску. **Приёмка:** выбранная услуга сохраняется от результата до итоговой заявки; изменение возможно только явным действием пользователя.

### A10. P1 — Обычный поиск сам меняет Москву на Аликанте

**Подтверждено браузером.** Из карточки перейти «Вернуться к сравнению» на `/services`, выбрать замену масла и нажать «Начать поиск». Получен URL `/services?service=oil-change&market=alicante` и ноль результатов, хотя до этого показывались московские сервисы. Пользователь город не менял.

**Где:** `autocareResultFilters.ts:44` подставляет старый идентификатор `ru-moscow`; `MarketSwitcher.tsx:39–59` не находит его среди `cityCode` и заменяет первым подходящим рынком.

**Последствия:** внезапно пустая выдача и потеря доверия к поиску. **Исправить:** один канонический идентификатор города, согласованный приоритет URL/сохранённого выбора; явная нормализация legacy-ID. **Приёмка:** поиск без market, возврат из карточки и изменение услуги не меняют выбранный город.

### A11. P1 — Production HTML не получает защитные заголовки

**Подтверждено на отдельной production-сборке.** У HTML главной, кабинетов и профилей отсутствуют CSP, X-Frame-Options/frame-ancestors и другие ожидаемые ограничения браузера. Helmet на API не защищает документ Next.

**Где:** `next.config.ts`; `scripts/check-security-headers.mjs` проверяет строковые признаки только backend-файлов. Доказательство — `production-http.json`.

**Последствия:** нет защиты страницы от встраивания, а внедрение стороннего скрипта не ограничено CSP. Наличие эксплуатируемого XSS этим аудитом не доказано.

**Исправить:** политика заголовков именно для HTML и статических ответов Next, с проверкой совместимости карт, изображений и авторизации. **Приёмка:** проверить реальный `next start`, отрицательный сценарий iframe и работу приложения; после появления edge-прокси повторить через публичный домен. HSTS проверить на HTTPS, а не требовать его от локального HTTP.

### A12. P2 — «Ближайшая запись» означает время открытия, а не свободный слот

**Подтверждено API/браузером.** В середине рабочего дня выдаётся `Today, 08:00`. `getDiscoverySlot` возвращает `schedule.open` до времени закрытия, не вычисляет ближайшее будущее свободное окно и не учитывает вместимость/длительность конкретной услуги. Проверка не использует blackout-даты.

**Где:** `server/src/modules/autocare/autocare-discovery.ts:19–32`.

**Последствия:** фильтр «Есть запись сегодня» и подпись ближайшего времени вводят в заблуждение, даже когда создание заявки будет защищено исправлением A02.

**Исправить:** отличать «работает сегодня», «запись по запросу» и фактический доступный слот. **Приёмка:** полностью занятый день, выходной, blackout, время после открытия и после закрытия показываются корректно.

### A13. P2 — Число мест в слоте выдумано интерфейсом

**Подтверждено браузером/кодом.** У филиала `appointmentCapacity=1`, но почти все слоты показывают «2 места», третий — «1 места». UI использует индекс: `index === 2 ? 1 : 2`, а не остаток вместимости.

**Где:** `ProviderRequestPanel.tsx:73`.

**Последствия:** ложная доступность и искусственная срочность решения. **Исправить:** использовать рассчитанную API вместимость либо убрать счётчик, если контракт возвращает только список времени. **Приёмка:** после занятия последнего места цифра и доступность меняются согласованно; для записи по запросу нет притворного числа свободных мест.

### A14. P2 — Гостю и клиенту без автомобиля показывается чужой BMW

**Подтверждено браузером.** Гостевая карточка сервиса показывает «Ваш автомобиль: BMW X5, 2021 / X5 xDrive30d…». В меню вошедшего клиента тоже BMW, хотя блок автомобилей сообщает «Автомобиль ещё не добавлен».

**Где:** `ProviderRequestPanel.tsx:80–89`, fallback-переводы `providerVehicleValue/providerVehicleDetails`, аналогичный fallback меню аккаунта.

**Последствия:** видимость утечки чужих данных, неверное понимание параметров заявки. Это демонстрационная строка, не доказанная выдача чужого автомобиля из базы.

**Исправить:** честное пустое состояние, реальный выбранный автомобиль и единый источник данных. **Приёмка:** новый клиент, гость и клиент с двумя автомобилями видят согласованное состояние во всех трёх местах.

### A15. P2 — Любому клиенту приписывались рейтинг 4.9 и 128 отзывов

### A38. P2 — Ошибка загрузки фото в запросе оценки теряется при переходе

**Подтверждено кодом; искусственный обрыв загрузки в браузере не выполнялся.** `EstimateRequestForm` отправляет текст, затем `Promise.allSettled` для фото. Даже если все фото не загрузились, записывает число ошибок в локальный state и сразу переходит в чат, размонтируя форму с предупреждением.

**Где:** `ProviderRequestPanel.tsx`, `EstimateRequestForm`, примерно строки 156–174.

**Последствия:** клиент считает, что описание и фотографии отправлены вместе, сервис получает только текст, повторить именно неудачные файлы негде.

**Исправить:** сохранить состояние частичной отправки и возможность повторить только отсутствующие вложения; сообщение не дублировать. **Приёмка:** один отказ из нескольких файлов виден после перехода и восстанавливается безопасным повтором.

### A39. P3 — «Самый высокий рейтинг» показывается при нуле отзывов

**Подтверждено браузером и кодом.** В выдаче у всех трёх сервисов 0.0/0 отзывов, но первый получает бейдж «Самый высокий рейтинг». `reduce` выбирает первый элемент без порога количества отзывов и без особой обработки ничьей.

**Где:** `ProviderResultsList.tsx:16–20`.

**Последствия:** пустая репутация выглядит как подтверждённое преимущество. **Исправить:** критерии достаточности данных и корректное поведение при равных значениях. **Приёмка:** при нуле отзывов бейджа нет; условия показа объяснимы пользователю.

### A40. P2 — «Выгодное предложение» привязано к mock ID, а скидка вычисляется из воздуха

**Подтверждено кодом; в проверенной реальной выдаче скидка не отображалась.** `ProviderResultsList` выбирает best-value только для `proservice-moscow`/`api-proservice-moscow`; реальные UUID туда не попадают. Если компонент получает этот highlight, `ProviderResultCard` сам рисует старую цену через умножение на 1.17 и бейдж −17%, без акции из API. Даже арифметически увеличение цены на 17% не равно скидке 17% от неё.

**Последствия:** реальный сценарий преимущества не работает, а шаблонный сценарий содержит выдуманную акцию. Это не доказанная ложная скидка на текущих реальных данных.

**Исправить:** отделить объективное сравнение предложений от промоакций; скидку брать из подтверждённых условий. **Приёмка:** одинаковые правила для UUID и любых названий; без акции нет зачёркнутой цены/процента, процент согласован со старой и новой ценой.

## Что нельзя считать проверенным production

Отсутствие домена сейчас не мешает исправлять перечисленные дефекты. Однако перед публичным запуском отдельно нужны доказательства:

- HTTPS/edge/CORS/cookies/OAuth redirect на фактических доменах, включая реальное поведение браузерных third-party cookies.
- Доставка писем через боевого отправителя и его DNS-настройки; восстановление доступа с реальным почтовым ящиком.
- Внешнее объектное хранилище, права доступа к приватным файлам, восстановление резервной копии в отдельном окружении.
- Worker под управлением production-процессов: перезапуск, лаг очередей, зависшие задачи, оповещения и повторы без дублей.
- Нагрузка и объёмы, близкие к ожидаемым; конкурентное бронирование и большие очереди модерации.
- Подтверждённые публичные контакты, тексты поддержки и юридические документы для выбранного оператора продукта. Локальный аудит не подтверждает владение указанными в макете телефоном или email.
