# Повторная проверка проекта — 20 ноября 2026

## Граница и результат

Проверен checkout `autocare-hub-local-pilot-remaining`: дерево его `HEAD`,
`origin/dev` и `origin/main` совпадало на начало проверки. Удалённые `dev` и
`main` сверены отдельно: после релизного PR #56 кодовых изменений не было.
Соседние checkout с незавершёнными локальными правками не изменялись.

**Вывод:** пилот с реальными пользовательскими данными остаётся **NO-GO**.
Найден новый release-blocking дефект начальных миграций. Зелёный CI и
сборка сами по себе не подтверждают безопасность пустой production-базы.

## Подтверждённые замечания

### P1 — известный пароль в активных учётных записях новой базы

`server/src/database/migrations/1781370793804-SeedInitialUsers.ts:5-16`
без условия по окружению добавляет `client@example.com`,
`owner@example.com`, `admin@example.com` с одинаковым bcrypt-хешем пароля
`123456`, статусом `active` и подтверждённым email. Локальная проверка
`bcryptjs.compareSync` подтвердила соответствие хеша этому паролю.
`server/src/database/data-source.ts:30-48` включает эту миграцию и для
`production`, а `render.yaml:8` запускает `release:migrate` перед запуском API.
Поздней миграции, удаляющей эти записи, не найдено. В
`server/src/modules/auth/auth.service.ts:310-343,380-425` клиент и владелец
проходят проверку пароля без административной MFA; для super-admin требуется
отдельный MFA-фактор. Это риск входа под предсказуемыми клиентской и
владельческой учётными записями **при развёртывании новой базы**. Состояние
какой-либо существующей production-базы не проверялось.

Исправление: не переписывать выполненную историческую миграцию без анализа
checksums. Добавить следующую миграцию, которая безопасно блокирует или
обезвреживает только сохранившиеся демонстрационные credentials, и gate,
запрещающий default credentials после миграции пустой базы. Затем повторить
изолированный PostgreSQL migration и login replay.

### P1 — демонстрационные объявления становятся публичными

`server/src/database/migrations/1781370829298-SeedCabinetsAndServices.ts:5-75`
и `1781591680138-SeedMoreCabinets.ts:5-78` создают 23 активных кабинета для
`owner@example.com`. `server/src/modules/cabinets/cabinets.routes.ts:111-117`
публикует каталог, а `cabinets.service.ts:191-201` выбирает активные записи.
Следовательно, после миграции пустой базы демонстрационные объявления
попадут в реальную выдачу, если endpoint доступен. Факт их присутствия в
какой-либо действующей базе не проверялся.

Исправление: в следующей миграции/релизной процедуре убрать только
идентифицированные demo-записи с сохранением пользовательских данных и
проверить отсутствие демообъявлений в публичном API после fresh migration.

### P2 — проверка демоданных не защищает основной Next build

`src/shared/config/api.ts:7-14` по умолчанию выбирает `mock`, а
`src/app/server-provider.ts:98-110` в таком режиме загружает публичные
демоданные. Обычный локальный `npm run build` дал Next artifact с семью
файлами, содержащими маркеры fixture; `check-production-fixture-leakage`
это обнаружил. В `.github/workflows/quality.yml:152-156` этот gate вызывается
только для Vite artifact. При явном `NEXT_PUBLIC_API_MODE=real` отдельный
Next build прошёл, и сканер проверил 193 файла без совпадений. Render frontend
задаёт `real` (`render.yaml:131-134`), но CI не доказывает отсутствие fixture
в самом production Next artifact. Конфигурация внешнего Vercel deployment не
проверялась.

Исправление: проверять Next artifact, собранный с release переменными, и
завершать production build ошибкой при отсутствующем/неверном API mode.

### P2 — публичный запрос всего каталога не ограничивает объём работы

`server/src/modules/cabinets/cabinets.routes.ts:117-119` предоставляет
анонимный `/cabinets/all`. `cabinets.service.ts:346-356` последовательно
запрашивает каждую страницу каталога по 50 записей и собирает весь результат
в память. Число запросов к БД и размер ответа растут вместе с каталогом;
каждая страница также рассчитывает preview доступности. После 1000 страниц
`getCabinetPagination` отвергнет следующий номер (`cabinet-pagination-policy.ts:1-11`),
поэтому каталог свыше 50 000 активных кабинетов приведёт к ошибке этого
маршрута. Текущий объём реальной БД и нагрузка не измерялись.

Исправление: перевести оставшегося клиента на постраничный API, затем убрать
или жёстко ограничить старый маршрут. Добавить проверку стоимости запроса и
поведения на границе страниц.

### P2 — поиск по доступности обрезает множество кандидатов

`server/src/modules/cabinets/cabinets.service.ts:289-297` при запросе
`availableToday`/`availabilityDate`/`durationMinutes` берёт только первые
`MAX_AVAILABLE_TODAY_CANDIDATES = 1000` кабинетов в порядке сортировки
(`availability-query-policy.ts:1`). Затем считает доступность и пагинацию
лишь по этой выборке (`cabinets.service.ts:315-337`). Если в базе более
1000 подходящих активных кабинетов, доступные записи за пределом выборки
не появятся в результатах. При этом schedules/booking previews читаются с
общими лимитами и без фильтра по выбранной дате до применения `take`, что
может исказить preview на больших объёмах. Текущий размер реального каталога
и частота этого сценария не проверены.

Исправление: вычислять доступность на стороне БД для всей подходящей выборки
с ограниченной пагинацией, фильтровать bookings по запрошенной дате до
лимита и проверять полноту результатов на границе 1000 кандидатов.

### P2 — ручной откат demo-миграций может удалить чужие записи

`server/README.md:150-153` рекомендует `npm run migration:revert`.
`1781370793804-SeedInitialUsers.ts:19-22` удаляет пользователей только по
email; `1781591680138-SeedMoreCabinets.ts:82-93` удаляет кабинеты по
шаблону названия `Professional Workspace %`. Если после первичного seed
соответствующий аккаунт или название используется реальными данными,
ручной откат может удалить их вместе с demo-записями. Автоматический
production-процесс использует прямые миграции, а не `revert`; риск относится
к ручной операции и инструкции в README.

Исправление: убрать общий совет об откате без проверки конкретной миграции;
для seed-данных использовать устойчивые идентификаторы/признаки и отдельно
документировать безопасную процедуру восстановления.

### P3 — текущая навигационная документация отстаёт от выпуска

`PROJECT_CONTEXT.md`, `docs/INDEX.md` и `docs/diagrams/README.md` сверху

следующую проверку к неактуальному коду. В датированных исторических секциях
старые сведения допустимы; обновить нужно текущую точку входа.
